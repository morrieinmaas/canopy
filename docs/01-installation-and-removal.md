# 01. Installation and removal

Back to the [README](../README.md). Next: [02 Commands](02-commands.md).

## Install

```sh
git clone https://github.com/morrieinmaas/canopy.git ~/.local/share/canopy
export PATH="$HOME/.local/share/canopy/bin:$PATH"
canopy install
```

Add the `PATH` line to your shell rc so it survives a new shell.

The clone can live anywhere. `bin/canopy` resolves its own store from the **real** path
of the running script: it follows the symlink chain of its own path first, then takes
the parent of the directory it lands in. So a symlink from a directory already on your
`PATH` works, and is the shorter route if you would rather not add one:

```sh
ln -s ~/.local/share/canopy/bin/canopy ~/.local/bin/canopy
```

The dispatcher is the entry point to symlink. It exports `CANOPY_STORE` before handing
off, so every `canopy <subcommand>` it dispatches inherits the store it resolved. The
`bin/canopy-*` files still derive their own store from `$(dirname "$0")/..`, so
symlinking one of them individually, rather than the dispatcher, does not work.

Requirements are tmux 3.4 or newer and a POSIX shell. Check yours first:

```sh
tmux -V
```

## Look before you install: `--dry-run`

`canopy install --dry-run` prints the plan and writes nothing at all. It is the same
plan the real run follows, generated by the same code.

On a machine with no tmux config:

```
$ canopy install --dry-run
create /home/you/.config/canopy/user.conf
create entry point /home/you/.config/tmux/tmux.conf, sourcing the store tmux.conf
write /home/you/.config/mise/conf.d/canopy.toml
run canopy-caps
run canopy-index
validate the resulting tmux config
```

On a machine that already has one:

```
$ canopy install --dry-run
create /home/you/.config/canopy/user.conf
own /home/you/.config/tmux/tmux.conf (backed up) and migrate it into /home/you/.config/canopy/user.conf
write /home/you/.config/mise/conf.d/canopy.toml
run canopy-caps
run canopy-index
validate the resulting tmux config
```

The `write .../mise/conf.d/canopy.toml` line appears only when `mise` is on your
`PATH` or that directory already exists. If canopy is already installed, the dry run
says so and exits 0.

## When you already have a tmux config

canopy owns the entry point tmux itself would load, by tmux's own precedence:

1. `~/.tmux.conf`, if it is a regular file
2. otherwise `~/.config/tmux/tmux.conf` (or `$XDG_CONFIG_HOME/tmux/tmux.conf`)

Whichever of those exists is the file canopy takes over. Install then refuses:

```
$ canopy install
canopy install found an existing tmux config and would migrate it:
create /home/you/.config/canopy/user.conf
own /home/you/.config/tmux/tmux.conf (backed up) and migrate it into /home/you/.config/canopy/user.conf
...
canopy: owning /home/you/.config/tmux/tmux.conf is a migration, not a merge; re-run with --yes to proceed
```

Exit status 1, and nothing on disk has changed. This is deliberate. Taking over an
entry point is a migration, not a merge, and canopy says so rather than pretending to
be additive.

Re-run with `--yes` and three things happen:

1. The original file is byte-copied into the transaction's `files/` directory.
2. Its contents are appended to `~/.config/canopy/user.conf`, under a dated comment
   naming where they came from.
3. The entry point is replaced with a short stub that sources canopy's `tmux.conf`.

The stub looks like this:

```
# canopy:entry-point: managed by canopy, do not edit directly.
# Any original content was migrated to /home/you/.config/canopy/user.conf.
...
set-environment -g CANOPY_STORE "/home/you/.local/share/canopy"
set-environment -g CANOPY_STATE "/home/you/.local/state/canopy"
set-environment -g CANOPY_CONFIG "/home/you/.config/canopy"
source-file "/home/you/.local/share/canopy/tmux/tmux.conf"
```

Every path in it is an absolute literal resolved at install time. tmux expands a
variable in a `source-file` path from the tmux **server's** environment, which nothing
outside tmux populates, so a stub written with `$CANOPY_STORE` in the path would load
nothing on a real machine. The `set-environment` lines are what put those three paths
into the server for everything the server starts later.

Your config is now sourced last, after every canopy default, so it still wins. See
[04 Configuration](04-configuration.md).

## When that config is a symlink into a dotfiles repo

chezmoi, stow and a bare dotfiles repo all leave `~/.config/tmux/tmux.conf` as a
symlink into a directory elsewhere. canopy owns the **link**, never the file at the
other end.

| Step | What canopy does |
|---|---|
| record | The manifest row stores `symlink:<target>`, not the target's hash |
| migrate | The bytes behind the link are copied into `user.conf` |
| own | The link is removed and a regular file is written in its place |
| restore | The link is recreated, pointing at the same target |

The file inside your dotfiles repo is never opened for writing at any point. Writing
through the link would modify a file canopy never recorded and therefore cannot
promise to restore.

A **dangling** symlink, which is what those tools leave behind when the source tree is
not checked out yet, is handled the same way. tmux skips such a link, so canopy would
be free to write straight over it; instead it recognises the link, refuses without
`--yes`, records it, and puts it back on restore, still dangling.

One ordering rule matters here. A dangling `~/.tmux.conf` never outranks a real
`~/.config/tmux/tmux.conf`. canopy looks for a loadable config first, and only then
for a dangling link, so it cannot end up owning a link while leaving the config you
actually load shadowed and unmigrated.

## What install validates before it commits

The last thing install does is start tmux on a throwaway socket, from an environment
holding nothing but `HOME`, `PATH` and `TMUX_TMPDIR`, and load **the entry point it
just wrote**. Not the store's own copy with this process's variables helpfully filled
in.

If that load fails, install runs the transaction's own `restore.sh`, marks the
transaction failed, and exits 1. Your original config is back before you see the error.

## Removal

```sh
canopy restore --all                 # every file back, byte for byte
rm -rf ~/.config/canopy              # your canopy overrides
rm -rf ~/.local/state/canopy         # restore points; the guarantee ends here
rm -rf ~/.local/share/canopy         # the clone
```

Then remove the `PATH` line from your shell rc.

Order matters. `canopy restore --all` reads the restore points out of
`~/.local/state/canopy`, so deleting that first leaves nothing to restore from.

There is no `canopy uninstall` command in M1. The four lines above are the whole of
it.

### What `canopy restore --all` leaves behind

Everything that existed before install is back. What remains is canopy's own state
tree:

```
~/.local/state/canopy/05-caps.conf
~/.local/state/canopy/commands.tsv
~/.local/state/canopy/backups/<id>/...
```

None of it existed before canopy, so none of it is covered by the restore guarantee,
and `backups/` has to survive for the guarantee to mean "forever". `~/.config/canopy`
is removed if canopy created it and you left nothing in it; if you put your own files
there, it stays, with them.

### If a file was edited after install

`canopy restore --all` will not silently overwrite work you did after canopy wrote a
file. It keeps that file, names it, and exits 1:

```
$ canopy restore --all
restore: 2 reverted, 1 kept
kept (changed since canopy wrote it): /home/you/.config/tmux/tmux.conf
```

Your choices are to move the edit somewhere safe and re-run, or to run
`canopy restore --all --force`, which reverts it after copying its current bytes into
a new restore point. Either way nothing is lost. See
[03 The restore guarantee](03-restore-guarantee.md).

## Reinstalling

`canopy install` refuses to run twice. It recognises its own stub by the
`# canopy:entry-point` marker and exits 1 without touching anything:

```
$ canopy install
canopy: canopy is already installed: /home/you/.config/tmux/tmux.conf already sources canopy's tmux.conf; nothing to migrate
```

To reinstall, restore first, then install again.
