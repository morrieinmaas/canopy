## The load order

`canopy install` writes a stub at the entry point tmux loads. That stub sets three
environment variables in the tmux **server** and sources one file, the store's
`tmux/tmux.conf`, which sources everything else in a fixed order:

| # | Sourced | From | Notes |
|---|---|---|---|
| 1 | `tmux/conf.d/00-core.conf` | the store | The deliberately small core. Not optional |
| 2 | `05-caps.conf` | `$CANOPY_STATE` | Generated by `canopy caps`. Sourced with `-q`, so a machine that never ran the probe still loads |
| 3 | `10-keys.conf` | `$CANOPY_STATE` | Generated by `canopy keys` from `tmux/keys.tsv`. Also `-q` |
| 4 | `tmux/conf.d/[1-9]*.conf` | the store | The numbered layers, glob-sorted. M2 ships two, `20-status.conf` and `30-plugins.conf` |
| 5 | `user.conf` | `$CANOPY_CONFIG` | Yours. Sourced last, so it wins |

Both generated layers live in `$CANOPY_STATE` rather than in the store's `conf.d`,
for one reason: the store is read-only by convention, and a generated file inside a
git checkout shows up as a local modification on every machine.

Two details in that table are load-bearing.

**Capabilities come second, before every layer.** A layer guarding on
`@canopy_has_fzf` has to see the option already set.

**The layer glob starts at `[1-9]`, not `[0-9]`.** `00-core.conf` was already sourced
in step 1, and re-sourcing it would be wrong rather than merely wasteful: `00-core`
uses plain `set -g`, which is idempotent, but later layers use appending forms
(`set -as terminal-features`, `set -ga`) that a second source would silently
duplicate. One rule for every layer file is easier to keep right than an exception.

`canopy doctor` asserts the last step textually against the store's own `tmux.conf`: the last
`source-file` line must target `user.conf`. If a future layer were added after it,
that check fails as a load-bearing failure and doctor exits 2.

## `~/.config/canopy/user.conf`

This file is yours. canopy creates it, and appends to it once during install if you
had an existing tmux config, and never writes to it again.

Because it is sourced last, everything in it wins over every canopy default. To
override a core setting, just set it:

```tmux
# ~/.config/canopy/user.conf
set -g mouse off
set -g history-limit 50000
set -g prefix C-a
```

The file created by an install that migrated an existing config looks like this:

```tmux
# canopy user config: sourced last, wins over every shipped default.

# canopy: migrated from /home/you/.config/tmux/tmux.conf on 2026-09-18
set -g @mine yes
```

Reload after editing:

```sh
tmux source-file ~/.config/tmux/tmux.conf
```

One thing does not work the way it looks: TPM plugin lists. `set -g @plugin
'owner/repo'` in this file loads nothing, because TPM finds plugins by grepping
config files one level below the entry point and this file is two levels down. Use
`set -g @tpm_plugins '...'`, which TPM reads from a real tmux option. `canopy doctor`
warns when it sees `@plugin` lines here; the full explanation is in
[05-troubleshooting.md](05-troubleshooting.md#my-tpm-plugins-stopped-loading-under-canopy).

`user.conf` survives uninstall unless you remove `~/.config/canopy` yourself. If you
put other files in that directory, `canopy restore --all` leaves the directory alone,
because it removes a directory only with `rmdir` and only if canopy created it.

## The key table

Every binding canopy ships is declared in one tab-separated file,
`tmux/keys.tsv`, and `canopy keys` generates `$CANOPY_STATE/10-keys.conf` from it.
Nothing else in canopy binds a key.

```
# name	key	flags	command	group	description
split-right	|	-	split-window -h -c "#{pane_current_path}"	pane	Split to the right, in the directory this pane is in
```

The reason it is a table rather than a file of `bind` lines is that a `bind` line
carries no name, no group and no description, so it can never appear in a
cheatsheet, a palette or a which-key menu. A row here has all four by
construction, and M4's surfaces read this same file instead of a second copy of
the truth.

`canopy keys --print` prints it as a grouped cheatsheet. The full column contract
and what happens to a malformed row is in
[02-commands.md](02-commands.md#canopy-keys).

Your own bindings go in `user.conf`, not in the table, and because `user.conf` is
sourced last they win over anything in it. Rebinding one of canopy's keys is a
`bind` line in `user.conf`; there is no need to edit the table.

## The status line

`20-status.conf` draws the status line, and every colour in it is read from an
option rather than written into the format string: `@theme_bg`, `@theme_fg`,
`@theme_blue`, `@theme_yellow`, `@theme_green`, `@theme_grey`, `@theme_muted`,
`@theme_red`, plus `@pill_l` and `@pill_r` for the pill end-caps. Set those in
`user.conf` and the whole bar repaints. That is the seam M5's theme layer is built
on.

`@pill_l` and `@pill_r` default to the empty string, so a terminal without a
powerline font renders plain text rather than replacement glyphs.

The right-hand end is one `#()` call into `canopy status`, never one per segment: a
status line that forks four processes every `status-interval` is a defect rather
than a style choice. Two segments can be turned off, and both default to on:

```tmux
set -g @canopy_status_battery off
set -g @canopy_status_net off
```

Replacing the bar wholesale is a `set -g status-right ...` in `user.conf`. One
warning if you do: tmux-continuum **prepends** its `#(continuum_save.sh)` call to
whatever `status-right` holds when it loads, and that interpolation *is* the
autosave. Setting `status-right` after canopy's plugin layer removes it, so put the
call back at the end of your own line. `canopy doctor` checks for it.

## What `00-core.conf` sets

The whole of it, today:

```tmux
set -g @canopy_test_marker shipped-default
set -g base-index 1
set -g pane-base-index 1
set -g escape-time 0
set -g focus-events on
set -g history-limit 100000
set -g mouse on
set -g renumber-windows on
```

`@canopy_test_marker` carries no behaviour. It exists so tests can prove `user.conf`
is sourced after this file and wins, without asserting on opinionated defaults that
will churn.

## The capability model

Detection runs once, when you run `canopy caps` (which `canopy install` does for
you). It writes plain tmux options to `$CANOPY_STATE/05-caps.conf`:

```tmux
set -g @canopy_has_wt 1
set -g @canopy_has_fzf 1
set -g @canopy_has_gum 0
set -g @canopy_has_ghostty 0
set -g @canopy_has_starship 1
set -g @canopy_has_mise 1
set -g @canopy_tmux_version 3.7b
```

| Tool | Layer it will enable |
|---|---|
| `wt` (worktrunk) | worktree |
| `fzf` | pickers and the command palette |
| `gum` | prompts |
| `ghostty` | terminal theming, opt-in per app |
| `starship` | prompt theming, opt-in per app |
| `mise` | the tool declaration fragment |

The point of writing detection to a file is that layer files guard on a tmux
**option**, never on a subprocess. Sourcing the whole config tree forks nothing, so
adding layers does not slow tmux startup.

A missing tool leaves its layer **dormant**, never broken. Dormant means the layer is
not loaded at all: zero bindings, zero formats, no half-states. `canopy doctor` names
which layers are dormant and why:

```
Layers:
  worktree (wt): active
  gum (gum): dormant (gum not found)
```

M1 ships no capability-gated layer yet. Until they exist, that section reports what
each capability will enable rather than what it currently does.

canopy never installs a missing tool. It declares and diagnoses dependencies; that is
all. If `mise` is present, install writes
`~/.config/mise/conf.d/canopy.toml` declaring `fzf`, `gum` and `starship` as tools,
so you can install them yourself with one `mise install`. Your own mise config is
never edited.

Re-run `canopy caps` after installing or removing any of those tools, then reload
tmux.

## Paths and environment variables

| Variable | Default | Holds |
|---|---|---|
| `CANOPY_STORE` | the clone. `bin/canopy` resolves it from the real path of the running script, following symlinks; the `bin/canopy-*` files resolve it from `$(dirname "$0")/..`, or inherit it from the dispatcher | The read-only distribution |
| `CANOPY_CONFIG` | `${XDG_CONFIG_HOME:-$HOME/.config}/canopy` | `user.conf`. Yours, survives uninstall |
| `CANOPY_STATE` | `${XDG_STATE_HOME:-$HOME/.local/state}/canopy` | Caps cache, command index, restore points |
| `CANOPY_RUNTIME` | `$XDG_RUNTIME_DIR/canopy`, else `/tmp/canopy-<uid>` | Scratch files. Created mode 0700 |

Every one of them must be an absolute path. A relative value is rejected by name
rather than resolved against some working directory canopy would have to guess:

```
$ XDG_CONFIG_HOME=relative/config canopy doctor
canopy: XDG_CONFIG_HOME must be an absolute path, got: relative/config
```

canopy records these paths verbatim into a manifest that outlives the process, and
`restore.sh` resolves manifest paths against whatever directory it is later run from,
so a relative value would produce a restore point naming a different file than the one
canopy backed up.

The runtime directory is checked, not just created. The `/tmp` fallback sits in a
world-writable directory, so canopy creates it with mode 0700 and refuses to use one
that is a symlink, is not a directory, is owned by another user, or is writable by
group or other:

```
$ canopy doctor
canopy: runtime directory /tmp/canopy-1000 is writable by group or other (mode 777), refusing to use it
```

Setting `CANOPY_*` is how the test suite points canopy at a scratch tree. It is not
something a normal install needs.
